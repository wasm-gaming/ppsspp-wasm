# 2026-08-23 15h22 · The contract, and the Emscripten port

The first session in this repository. It was empty — no commits, no branches, not even on the
remote — so everything below is new.

Two pieces of work that were deliberately kept apart: the `@wasm-gaming/engine-specs` contract
implemented over PPSSPP, and the beginning of porting PPSSPP itself to Emscripten. They meet at
one file, [`src/module.ts`](../src/module.ts), and that seam is the reason the first could be
finished while the second is nowhere near.

## What was asked

> el objetivo es implementar PPSSPP en este repo como webassembly respetando el contrato de
> engine-specs

Three decisions were taken before any code was written:

1. **A fork of our own from `hrydgard/ppsspp`**, rather than consuming a prebuilt artifact or
   tracking the unofficial `root-hunter` fork.
2. **Scope for the session:** scaffolding plus the SDK against an injectable loader, conformance
   and runtime tests green, and a demo. The C++ build wired but not run.
3. **`engine-specs` conventions, minus the session-first workflow** — stack, CI and code
   conventions copied; approval-before-work not adopted.

Point 2 was overtaken by events, in a good way: the C++ build was not only wired but driven
through six CI rounds. See *The build, round by round*.

## Where this repo actually was

Empty. `git ls-remote` returned nothing. The contract lives in a separate repository,
`wasm-gaming/engine-specs`, published as `@wasm-gaming/engine-specs@0.3.2` on npm — so it is a
normal runtime dependency here, not a vendored copy.

Three findings from reading the ground before starting, each of which shaped what followed:

**PPSSPP upstream has no Emscripten support.** Not partial — none. At the pinned revision there
is no `EMSCRIPTEN` branch anywhere in the 1715-line `CMakeLists.txt` and no file named for wasm
or the web. [Issue #13567](https://github.com/hrydgard/ppsspp/issues/13567) is still a question
rather than a plan. So `native/` is a port, not a configuration.

**But the port is known to be achievable.** The unofficial fork
[`root-hunter/ppsspp-wasm`](https://github.com/root-hunter/ppsspp-wasm) (branch `wasm`) reached a
playable browser build, and its CMake shape was the starting point for ours. **That reference is
dated**, which cost a round later: it is based on a PPSSPP that still used SDL2.

**PPSSPP is GPL-2.0-or-later**, and `engine-specs` is MIT. Vendoring or deriving from PPSSPP
makes this repository GPL-2.0+. `LICENSE.TXT` is PPSSPP's own, attribution intact.

## A · The contract implementation

Everything the contract prescribes — state, descriptors, cumulative merge, the chainable promise,
the channel — is inherited from `EnginePlayBase` and `EngineSDKBase`. What is written here is the
part that is about running a PSP emulator in a browser.

**The four payloads, closed.** `config` is how the emulator runs and survives a game; `options` is
what one session opens with; `assets` are files; `storage` is where the memory stick lives. No
index signatures, so a host writing a key PPSSPP does not have stops compiling.

**`src/settings.ts` is the only file that knows PPSSPP's vocabulary.** A host says
`textureFiltering: 'linear'`; the ini says `TextureFiltering = 3`. Every key came from
`Core/Config.cpp` and every integer from `Core/ConfigValues.h` — read, not guessed. Where no
setting existed it was not invented: **there is no `VSync` key in `Config.cpp`**, so the property
was dropped rather than fabricated. `resume` and `stateSlot` collapse into one number because
`Core/Config.h:361` says `iAutoLoadSaveState` is *"0 = off, 1 = oldest, 2 = newest, 3+ = slot
number + 3"*.

**`assets.game` takes `Blob | Uint8Array`, and the order matters.** A PSP ISO runs to 1.8 GB
against a 4 GB wasm heap ceiling. A `Blob` is mounted through WORKERFS and read lazily; a
`Uint8Array` is copied and costs its size again. Both work; only one works for a full-size disc.
Format is sniffed from magic bytes, because a host that fetched a game over the network has a
`Blob` with no name at all.

**No JIT is offered, and that is a contract decision, not an omission.** WebAssembly cannot
generate code at runtime, so `cpuCore` offers only the two interpreters. Offering `jit` would be
offering a crash.

### Two consequences of Emscripten that shaped the code

**`main()` runs once.** There is no supported way to run an Emscripten `main()` twice, so
`restart()` cannot mean "tell the emulator to reboot" — it disposes of the module and builds
another. This is the one place the contract's chainable `restart()` costs far more than it reads
like it should.

**A canvas yields one WebGL context for its entire lifetime.** So every restart also builds a
*new* canvas. Reusing it would fail exactly where the picture is supposed to appear, with an
error that says nothing about why.

## B · The native port

`native/` holds a pinned upstream revision (`native/UPSTREAM`) plus a patch series, rather than a
submodule or a vendored tree: the pin is readable in `git log`, the series is the whole of what we
change, and nobody working on the JavaScript pays for a 1 GB clone.

Three patches so far, each described in [`native/README.md`](../native/README.md).

## Walkthrough · as built

```
src/module.ts     the seam — what the Emscripten build must export
src/payloads.ts   the four payloads, closed
src/spec.ts       the descriptors; `default` lives here and nowhere else
src/settings.ts   host vocabulary → PPSSPP's ini
src/assets.ts     Blob or bytes → a path PPSSPP can open
src/loader.ts     the real loader, lazily importing the generated glue
src/ppsspp-wasm.ts  PpssppSDK / PpssppPlay
native/           UPSTREAM pin, patches/, and the port's own README
demo/             a host that contains no PPSSPP setting names at all
```

**The seam is the specification.** `src/module.ts` is not a convenience type: it declares what the
build must export, `tests/fake-module.mjs` implements the same declaration in ~160 lines, and the
whole lifecycle is therefore exercised in Node with no `.wasm` anywhere. When the native side
needs a new capability it is declared there first.

**The loader is a constructor parameter, not an import.** `new PpssppSDK(init, loader)` — an extra
*optional* parameter, which was checked against `tsc` before being relied on: a class with one
still satisfies `EngineSDKConstructor`, so the conformance check does not weaken.

**The demo is the argument for the descriptors.** Its settings panel is generated entirely from
what `config()`, `options()`, `assets()` and `storage()` report — types, choices, descriptions,
and whether each applies live. Eighteen controls, seven "restart" badges matching exactly the
seven `live: false` properties, and file inputs whose `accept` comes from `allowedTypes`. Point it
at another engine and it paints that engine's settings.

### Bugs found by building, not by reading

1. **An abort during module instantiation had nowhere to land.** `#booted` was armed just before
   `callMain`, so an Emscripten abort during runtime init — which arrives through `onAbort` — was
   emitted as an event while `open()` sailed on and waited forever for a first frame. The deferred
   is now armed *before* the module is built and raced against the boot work. Found by a test
   written for exactly that case, which hung.
2. **The memory stick path had `PSP` twice.** `#writeAssets` was passed `<userDir>/PSP` and then
   appended `/PSP/PPSSPP_STATE`, so a save state was written where PPSSPP would never look.
3. **The published package could not resolve its own emulator.** `src/loader.ts` resolves the glue
   relative to itself — `dist/native/ppsspp.js` once compiled — while `make wasm-build` copied the
   artifacts to `src/native/`. Nothing would ever have looked there. Found while writing
   `release.yml`, which is what made the question "can this actually be released" concrete.
4. **`files: ["dist/", "src/"]`** would have shipped tens of megabytes of build output twice.
5. **The demo could not resolve a bare specifier.** `dist/` imports `@wasm-gaming/engine-specs` by
   name and a browser cannot resolve that. Found by opening the page, not by reading it — the
   panel silently rendered nothing. Fixed with an import map and a copy in `site/vendor/`, no
   bundler involved.
6. **`INCOMING_MODULE_JS_API` takes only names Emscripten knows.** Listing `ppssppEvent` and
   `pthreadPoolSize` there earned `invalid entry` warnings. It does not matter — `MODULARIZE`
   emits `var Module = moduleArg`, so a host's own properties arrive on the module regardless —
   but the declaration was wrong and is now the runtime's own names only.

### A decision that was wrong, and how it was corrected

Round 3 of the build hit x86 intrinsics in `ext/at3_standalone`. The response was to enable
Emscripten's SSE-to-wasm translation with `-msse -msse2`, on the reasoning that it is a supported
feature and keeps the vectorised audio decode. It compiled, and it was the wrong call.

One target later `Common/CommonFuncs.h` included `<x86intrin.h>` — the kitchen-sink header — which
pulls in `ammintrin.h` (SSE4a) and `fma4intrin.h` (FMA4). No wasm toolchain implements those and
none will. There is no flag that gets past it; `-msse3` and friends would only have moved the wall.

The cause was upstream's own `ppsspp_config.h`, which maps `__EMSCRIPTEN__` to `PPSSPP_ARCH_X86`
with `PPSSPP_ARCH_SSE2` — reasonable when the target was asm.js, false now. Patch 0002 gives wasm32
its own `PPSSPP_ARCH_WASM`, modelled on the `RISCV64`, `MIPS` and `LOONGARCH64` branches already
sitting beside it, so it is the idiomatic shape for that codebase rather than an exception carved
for us. `-msse`/`-msse2` were dropped in the same patch: nothing reaches for x86 intrinsics any
more, and leaving them would advertise a capability the build does not use.

**The lesson, written down so it is not re-derived:** the SSE approach treated a symptom that
upstream's architecture claim was producing. Deferring the structural fix cost a round.

### A bug in upstream, not in the port

`Common/Math/CrossSIMD.h:1682` calls `LoadR24x3_One`, which exists nowhere in the tree. The real
name is `LoadF24x3_One`. It sits in the scalar fallback, which only compiles on a target with
neither SSE nor NEON — so this build is the first to reach it, and the typo has never been caught.

**Correcting the name alone would compile and be wrong.** The SSE, NEON and LOONGARCH
implementations of `LoadF24x4` all shift four lanes left by 8; `LoadF24x3_One` loads three and
zeroes W. Patch 0003 writes out the four-lane semantics the other three share.

This one is independent of WebAssembly and should be sent to `hrydgard/ppsspp` on its own.

## The build, round by round

Each round is a CI dispatch of `wasm.yml`; the local sandbox cannot build (see *Verified, and not*).

| Round | Reached | Wall |
| --- | --- | --- |
| 1 | configure | `find_package(SDL3)` — upstream now requires SDL3, no SDL2 fallback |
| 2 | 147/1118 | `ext/armips`: ghc::filesystem does not know Emscripten |
| 3 | 319/1118 | `at3_standalone`: SSE2 intrinsics |
| 4 | 325/1118 | `CommonFuncs.h` → `<x86intrin.h>` (SSE4a, FMA4) |
| 5 | 692/1118 | `CrossSIMD.h`: call to a function that does not exist |
| 6 | 699/1118 | not yet read |

Round 1's failure also killed an assumption inherited from the reference fork: **`-sUSE_SDL=2` is
wrong for the pinned revision**, and `USE_SYSTEM_LIBSDL2` no longer exists as an option — we were
passing a dead flag. Emscripten does carry `-sUSE_SDL=3` and `-sUSE_SDL_TTF=3`, they are in the
`emsdk:5.0.7` image, they build SDL 3.4.2, and there is an `sdl3-mt` variant for threads. The
port is marked experimental, and `find_package(SDL3)` can never find it, because an Emscripten
port is a compile flag rather than a CMake config package.

## Verified, and not

**Verified.** `make test` from a clean tree: 38 runtime tests, the compile-time conformance suite
(`tests/conformance.ts` drives the engine as a host would; `tests/types.test-d.ts` pins what must
*not* compile), and the demo held to the contract through `checkJs`. `make site` with zero typedoc
warnings. The demo driven end to end in a real Chromium: the panel generated from descriptors
alone, a live change reaching the bridge as a `ccall`, the canvas replaced on restart, the memory
stick flushed on destroy, an anonymous `Blob` sniffed to `.cso` from its bytes, and no console
errors. `npm pack`: 38 files, 45.2 kB, all seven sources present and no build output duplicated.

The Emscripten link flag set was validated against a real `emcc` link of a hello-world **before**
spending build rounds on it, which is how the `INCOMING_MODULE_JS_API` mistake surfaced and how
`-sPTHREAD_POOL_SIZE=Module['pthreadPoolSize']||…` was confirmed to be emitted verbatim into the
glue — so `config.threads` genuinely sizes the worker pool rather than merely claiming to.

Each native patch was reproduced and verified in isolation under `em++` before being pushed: the
ghc header fails to compile as upstream ships it and compiles with the two defines;
`Common/CommonFuncs.h` fails before patch 0002 and compiles after.

**Not verified, and these are real caveats.**

- **Nothing has linked.** 699 of 1118 targets compile. Linking is untouched, and `SDLMain.cpp`,
  the GL backend and the main loop — where Emscripten needs `emscripten_set_main_loop` rather than
  a blocking `while` — are all still ahead.
- **The bridge does not exist.** No `ppsspp_web_*` is implemented, which is why
  `-sEXPORTED_FUNCTIONS` is deliberately absent: naming a symbol that does not exist is a link
  error.
- **The SDK has never run against real PPSSPP.** Every test and the demo run against a fake or a
  stub that satisfies `src/module.ts`. The contract implementation is proven against its own
  declaration, not against the emulator.
- **A local build is blocked.** The Emscripten SDL3 port is fetched from
  `https://github.com/libsdl-org/SDL/archive/release-3.4.2.zip`, which this sandbox's egress
  policy refuses with HTTP 403. Reported rather than routed around, per the proxy's own guidance.
  CI has no such restriction, which is why every round costs 7–15 minutes instead of seconds.
- **Round 6's specific error was not read**, only its target count.

## Loose ends, deliberately left

- **`main` does not exist on the remote.** All of this is on
  `claude/engine-specs-review-qrjlz3`. `release.yml`'s publish job is gated on
  `refs/heads/main`, so it cannot run until that branch exists.
- **No PR opened**, because none was asked for.
- **`MASKED_PSP_MEMORY` is redefined** on every GPU translation unit — a warning, from upstream's
  own `USE_NO_MMAP` block meeting `Core/MemMap.h`. Left alone: it is upstream's, and it is noise
  rather than a defect.
- **`engine-specs` has two of its own loose ends** noticed while reading it: `AGENTS.md` links to
  a `STACK.md` that does not exist, and its "capitular" flow writes to `README.md` sections
  (`# Project Specs`, `# Todos`) that are not there either. Not ours to fix from here.
- **The dist-tag question.** `release.yml` defaults to `next` rather than `latest`, because the
  package cannot start a session in a browser yet. A dist-tag does not affect `^` range
  resolution, so if anyone ever depends on this before the emulator ships, prerelease versions
  (`0.2.0-rc.1`) become the right answer instead.

# Extension · 2026-08-23 · closing rule for session files, and a rename that was reverted

**Summary.** `SESSIONS/` gains a completion rule, and a proposed rename of the folder to
`ROADMAP/` was carried out and then reverted within the same session.

## The closing rule

A file is now understood as one **body of work**, not one sitting — several sessions may extend
it, and one session may open more than one. When everything it set out to do is done:

1. Append a final `## Walkthrough · as completed` — what landed across the whole body of work,
   not a summary of what was planned.
2. Rename it from `.session.md` to `.session.completed.md`.

Read at a glance, the folder then answers the two questions that matter: `*.session.md` is open,
`*.session.completed.md` is finished. Nothing is deleted and nothing leaves the folder.

A file closes only when its `Next` is empty. Work being **abandoned** rather than finished is
said so in the walkthrough: an abandoned item closed quietly is indistinguishable from a
forgotten one.

This also fixes a real gap noted earlier in this session — that "what remains" was scattered
across four documents with no single place to look. `Next` is now a required section rather than
one this file happened to have, and the open/closed split makes the folder itself the index.

## The rename, and why it was reverted

`SESSIONS/` was renamed to `ROADMAP/` and the files stripped of their `.session` infix, on the
reasoning that the completion rule turns these files into forward-looking plans rather than
backward-looking records, and that a folder called `SESSIONS` undersells that.

Reverted immediately afterwards, on the author's call. `SESSIONS/` it is, and the `.session.md`
naming stays — which also keeps it consistent with `engine-specs`, where the convention came
from, and where a reader of one repository can navigate the other without relearning anything.

Recorded rather than quietly undone, because it is exactly the kind of turn this rule exists to
preserve: the completion rule survived the rename being dropped, and the two were separate
decisions that could easily be misremembered as one.

### Correction · 2026-08-23 · the `.session` infix is dropped

Files in `SESSIONS/` are named `YYYY-MM-DD_HHhMM.<summary>.md`, and close as
`.completed.md`. The `.session.md` naming described in the extension above is superseded: the
folder already says what these are, so the infix repeated it, and `.session.completed.md` was
the clumsier half of a rule meant to be read at a glance.

This is a divergence from `engine-specs`, which does use `.session.md`. Accepted deliberately —
that repository has no closing rule, so it never had to spell one out on the end of a file name.
