## Where this repo actually was

one object.

**The smoke test only runs in CI**, and not for convenience: the artifact download is
refused for this account's sessions, so the emulator and a browser cannot be put in the
same place by hand. `make smoke-selftest` needs no emulator and does run locally, which
is what makes the instrument itself cheap to change.

## The pending register

Superseding every `Next` list in the closed file.

### Blocking the port from being usable

1. **Explain the pixel sampler's disagreement, or prove a host cannot hit it.** The
   screenshot shows 1552 colours; the in-page `drawImage` sampler reads the same canvas
   as having no opaque pixel. The leading explanation is the context attributes —
   `alpha: true` with `premultipliedAlpha: true`, so a drawing buffer left at zero alpha
   contributes nothing when *we* composite it — but SwiftShader's handling of `drawImage`
   from a WebGL canvas would fit too, and **neither has been established**. This matters
   beyond the instrument: a host that composites this canvas the way the sampler does
   would see the same nothing. `SDL_GL_SetAttribute(SDL_GL_ALPHA_SIZE, 0)` under
   Emscripten is the obvious experiment, and it belongs in the port rather than the
   harness — forcing it in the harness would turn the smoke test green while everything
   the package ships stayed broken.

2. **Give SDL3 a canvas it can find.** Its Emscripten driver resolves
   `SDL_HINT_EMSCRIPTEN_CANVAS_SELECTOR`, defaulting to `#canvas`, and fails window
   creation when nothing matches. The smoke harness uses that id to test one thing at a
   time; the SDK cannot, because it builds a new canvas per restart and they cannot all
   share an id. Cheapest shape scouted: export `ENV` and set
   `SDL_EMSCRIPTEN_CANVAS_SELECTOR` before `callMain` — one more name in
   `-sEXPORTED_RUNTIME_METHODS`, no new C. Either way it is a change to `src/module.ts`,
   **and that is where it must be declared first.**

3. **The bridge, and `-sEXPORTED_FUNCTIONS`.** Design scouted in the source, not written:
   - `Core/Config.cpp` already has the table this needs — `g_sectionMeta`, mapping
     `"Graphics"` and friends to their `ConfigSetting` arrays — and
     `ConfigSetting::ReadFromIniSection()` already applies a value from an ini section. A
     function beside that table taking `Section`, `Key` and a string is the whole of the
     settings half.
   - A new EMSCRIPTEN-only source holds the four `ppsspp_web_*` symbols with
     `EMSCRIPTEN_KEEPALIVE`, plus the event callback. Events must reach
     `Module.ppssppEvent` from threads that are not the main one, so
     `MAIN_THREAD_ASYNC_EM_ASM` rather than a plain `EM_ASM`.
   - `Web/FastForward` has no ini entry — it is this package's own key and sets the
     throttle, not a config field.
   - `booted` is the one event with a hard requirement: emitted when the first frame is on
     its way, not when `main()` starts, because it is what resolves `start()`.

4. **Wire the real loader and drop the demo's stub** — the first moment the two halves of
   this repository touch. `make site` will need to carry `dist/native/`; it copies
   `dist/*.js` only, so the glue would 404 where `src/loader.ts` looks for it. The `.data`
   bug from the first session is the standing argument for doing this: the stub is why
   nobody found it.

5. **Boot a game.** Everything measured so far is PPSSPP's own UI. The smoke test runs
   `callMain([])` and drives no input, so nothing past the menu has ever been exercised.

### Where this repo actually was

```

Context attributes: {"alpha":true, … ,"premultipliedAlpha":true,"preserveDrawingBuffer":true, …}
```

`0 opaque` is not "the sampler failed". It is 481 samples in which every pixel came
back `(0,0,0,0)`, which is a specific claim about the drawing buffer and not about the
instrument.

### Walkthrough · as built

**The mechanism.** A WebGL drawing buffer with `alpha: true` and
`premultipliedAlpha: true` is composited against the page as premultiplied data. PPSSPP
never writes alpha into the backbuffer, so the buffer holds the picture in RGB with
alpha 0 everywhere, and both readings follow from that one fact:

- on screen, `dst = src.rgb + page.rgb * (1 - 0)` — the picture is *added* to the page,
  and it looks perfect;
- anywhere else, `drawImage` into a transparent target gives `src.rgb` at alpha 0, and
  `getImageData` un-premultiplies that back to `(0,0,0,0)`.

Which of the two a consumer gets depends only on whether it is the browser compositing
the canvas onto its own page. Embedding the canvas — which is the whole of what this
package does — lands on the second.

**The proof, and it needs no emulator.** `tests/fakes/transparent/` is
`tests/fakes/draws/` with one argument changed: the bands are cleared with alpha 0
instead of 1. It reproduces round 26's fingerprint exactly — colour in the screenshot,
`0 opaque`, `best 1 colours` — in twelve seconds on a laptop. The pair is the
experiment: same browser, same SwiftShader, same `drawImage`, same context attributes,
one different argument. `draws/` is read back directly and `transparent/` is not, so
the sampler and the browser are both exonerated by their own agreement on the control.

**The instrument now names the cause instead of reporting a disagreement.** The runner
samples a second time onto an **opaque backdrop**. A buffer carrying colour at alpha 0
composites to nothing on a transparent target and to its own colour on an opaque one,
because the backdrop supplies the alpha that was never written; a canvas the sampler
genuinely cannot read comes back flat both times. That is one `drawImage` and it
separates a finding about the port from a finding about the runner. When it lands on
the first the verdict is `DRAWING, BUT TRANSPARENT` and the round is **red** — this
package ships a canvas, not a tab, and a green round for a picture no host can see is
exactly the kind of green tick the smoke test exists to refuse.

**The fix is one line of SDL vocabulary.** SDL3 defaults `SDL_GL_ALPHA_SIZE` to 8, and
`src/video/emscripten/SDL_emscriptenopengles.c` passes `gl_config.alpha_size > 0`
straight into the WebGL context attributes. Patch 0013 asks for 0 under
`__EMSCRIPTEN__`, beside the other attribute calls in `SDL/SDLMain.cpp`. PPSSPP never
calls `SDL_GL_ResetAttributes`, so the value set in `main()` is still there when
`SDL_GL_CreateContext` reads it.

It belongs in the port and not in the harness, and that is the same argument the
register made: forcing `alpha: false` where the *instrument* creates its context would
have turned the smoke run green while everything the package ships stayed invisible.

## Extension · 2026-08-24 · The seam, widened once

Items 2 and 3 of the register, together, because both were changes to
[`src/module.ts`](../src/module.ts) and the closed file was explicit that the seam should
be widened once rather than twice.

### Walkthrough · as built

**The canvas half is a hint, and it needed no C.** SDL3 resolves the selector in
`Emscripten_CreateWindow`:

```c
selector = SDL_GetHint(SDL_HINT_EMSCRIPTEN_CANVAS_SELECTOR);
if (!selector || !*selector) {
    selector = SDL_GetStringProperty(props, SDL_PROP_WINDOW_CREATE_EMSCRIPTEN_CANVAS_ID_STRING, "#canvas");
}
```

Two ways in, where the register knew of one. `SDL_GetHint` reads the environment before
its own hint table, so `Module.ENV` is enough: `PpssppModuleInit` gains
`canvasSelector`, the loader writes it into `ENV` after instantiation and before
`callMain` — in time, because the window is not created until `main()` runs — and `ENV`
joins `-sEXPORTED_RUNTIME_METHODS`. The second way, the window-creation property, is per
*window* rather than per process and is the better fit for a package that builds a new
canvas per session; it is also a patch to PPSSPP's own `SDL_CreateWindow` call. The hint
needs nothing from upstream, so the hint is what is here, and the alternative is written
down in `src/loader.ts` beside the line that uses it.

Each session's canvas now carries `ppsspp-canvas-N`. A restart builds a new canvas
because a canvas hands out one WebGL context for its whole life, and the selector has to
follow it there — a reused one would point the second module at the spent element.

**The bridge is one function on one thread.** `PpssppWeb::Frame()` is called from
SDLMain's Emscripten main loop, which is the browser's main thread: the only thread from
which a call into JS is legal and where the page's callback can run. Everything
observable is polled there — the boot completing, the frame rate, PPSSPP's own pause
menu, the frontend returning to its game list — and everything else is queued under a
mutex and drained there.

That shape is why the register's own scouting note about `MAIN_THREAD_ASYNC_EM_ASM` did
not survive contact: it is needed only if events are emitted from the thread that
produced them, and none are. Two producers cannot be polled and are hooked instead, both
three lines: a failed boot in `Core/System.cpp`, at the one point where the error string
still exists before the caller consumes it and the boot state goes back to `Off`; and
`Core/SaveState.cpp`, where `SaveSlot` and `LoadSlot` wrap the caller's own callback, so
a host hears about save states however they were triggered.

**The settings half was already written, in PPSSPP.** `SetConfigValueFromString` sits
beside `g_sectionMeta` in `Core/Config.cpp` and is a lookup plus a one-entry ini section
for `ConfigSetting::ReadFromIniSection` to read the value out of. No second copy of the
type switch, and an unknown section or key returns 0 rather than being swallowed.

**Pause is PPSSPP's own.** `Core_Break(BreakReason::UIPause)` and `Core_Resume`, which is
what `VIRTKEY_PAUSE_NO_MENU` does in `UI/EmuScreen.cpp`. Emulation stops, the last frame
stays on the canvas, no screen is pushed. `Web/FastForward` sets
`PSP_CoreParameter().fastForward`, which is what the throttle actually reads and what the
WebSocket debugger's `GameSubscriber` sets for the same purpose.
