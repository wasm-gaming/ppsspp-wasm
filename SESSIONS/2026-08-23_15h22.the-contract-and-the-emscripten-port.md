# 2026-08-23 15h22 · The contract, and the Emscripten port

The first session in this repository. It was empty — no commits, no branches, not even on the
remote — so everything below is new.

Two pieces of work that were deliberately kept apart: the `@wasm-gaming/engine-specs` contract
implemented over PPSSPP, and the beginning of porting PPSSPP itself to Emscripten. They meet at
one file, [`src/module.ts`](../src/module.ts), and that seam is the reason the first could be
finished while the second is nowhere near.

## What was asked

Three decisions were taken before any code was written:

1. **A fork of our own from `hrydgard/ppsspp`**, rather than consuming a prebuilt artifact or

## Where this repo actually was

Empty. `git ls-remote` returned nothing. The contract lives in a separate repository,
`wasm-gaming/engine-specs`, published as `@wasm-gaming/engine-specs@0.3.2` on npm — so it is a
normal runtime dependency here, not a vendored copy.

Three findings from reading the ground before starting, each of which shaped what followed:

**PPSSPP upstream has no Emscripten support.** Not partial — none. At the pinned revision there
is no `EMSCRIPTEN` branch anywhere in the 1715-line `CMakeLists.txt` and no file named for wasm
or the web. [Issue #13567](https://github.com/hrydgard/ppsspp/issues/13567) is still a question
rather than a plan. So `native/` is a port, not a configuration.

**But the port is known to be achievable.** The unofficial fork
[`root-hunter/ppsspp-wasm`](https://github.com/root-hunter/ppsspp-wasm) (branch `wasm`) reached a
playable browser build, and its CMake shape was the starting point for ours. **That reference is
dated**, which cost a round later: it is based on a PPSSPP that still used SDL2.

**PPSSPP is GPL-2.0-or-later**, and `engine-specs` is MIT. Vendoring or deriving from PPSSPP
makes this repository GPL-2.0+. `LICENSE.TXT` is PPSSPP's own, attribution intact.

## A · The contract implementation

Everything the contract prescribes — state, descriptors, cumulative merge, the chainable promise,
the channel — is inherited from `EnginePlayBase` and `EngineSDKBase`. What is written here is the
part that is about running a PSP emulator in a browser.

**The four payloads, closed.** `config` is how the emulator runs and survives a game; `options` is
what one session opens with; `assets` are files; `storage` is where the memory stick lives. No
index signatures, so a host writing a key PPSSPP does not have stops compiling.

**`src/settings.ts` is the only file that knows PPSSPP's vocabulary.** A host says
`textureFiltering: 'linear'`; the ini says `TextureFiltering = 3`. Every key came from
`Core/Config.cpp` and every integer from `Core/ConfigValues.h` — read, not guessed. Where no
setting existed it was not invented: **there is no `VSync` key in `Config.cpp`**, so the property
was dropped rather than fabricated. `resume` and `stateSlot` collapse into one number because
`Core/Config.h:361` says `iAutoLoadSaveState` is *"0 = off, 1 = oldest, 2 = newest, 3+ = slot
number + 3"*.

**`assets.game` takes `Blob | Uint8Array`, and the order matters.** A PSP ISO runs to 1.8 GB
against a 4 GB wasm heap ceiling. A `Blob` is mounted through WORKERFS and read lazily; a
`Uint8Array` is copied and costs its size again. Both work; only one works for a full-size disc.
Format is sniffed from magic bytes, because a host that fetched a game over the network has a
`Blob` with no name at all.

**No JIT is offered, and that is a contract decision, not an omission.** WebAssembly cannot
generate code at runtime, so `cpuCore` offers only the two interpreters. Offering `jit` would be
offering a crash.

### Two consequences of Emscripten that shaped the code

**`main()` runs once.** There is no supported way to run an Emscripten `main()` twice, so
`restart()` cannot mean "tell the emulator to reboot" — it disposes of the module and builds
another. This is the one place the contract's chainable `restart()` costs far more than it reads
like it should.

**A canvas yields one WebGL context for its entire lifetime.** So every restart also builds a
*new* canvas. Reusing it would fail exactly where the picture is supposed to appear, with an
error that says nothing about why.

## B · The native port

`native/` holds a pinned upstream revision (`native/UPSTREAM`) plus a patch series, rather than a
submodule or a vendored tree: the pin is readable in `git log`, the series is the whole of what we
change, and nobody working on the JavaScript pays for a 1 GB clone.

Three patches so far, each described in [`native/README.md`](../native/README.md).

## Walkthrough · as built

```
src/module.ts     the seam — what the Emscripten build must export
src/payloads.ts   the four payloads, closed
src/spec.ts       the descriptors; `default` lives here and nowhere else
src/settings.ts   host vocabulary → PPSSPP's ini
src/assets.ts     Blob or bytes → a path PPSSPP can open
src/loader.ts     the real loader, lazily importing the generated glue
src/ppsspp-wasm.ts  PpssppSDK / PpssppPlay
native/           UPSTREAM pin, patches/, and the port's own README
demo/             a host that contains no PPSSPP setting names at all
```

**The seam is the specification.** `src/module.ts` is not a convenience type: it declares what the
build must export, `tests/fake-module.mjs` implements the same declaration in ~160 lines, and the
whole lifecycle is therefore exercised in Node with no `.wasm` anywhere. When the native side
needs a new capability it is declared there first.

**The loader is a constructor parameter, not an import.** `new PpssppSDK(init, loader)` — an extra
*optional* parameter, which was checked against `tsc` before being relied on: a class with one
still satisfies `EngineSDKConstructor`, so the conformance check does not weaken.

**The demo is the argument for the descriptors.** Its settings panel is generated entirely from
what `config()`, `options()`, `assets()` and `storage()` report — types, choices, descriptions,
and whether each applies live. Eighteen controls, seven "restart" badges matching exactly the
seven `live: false` properties, and file inputs whose `accept` comes from `allowedTypes`. Point it
at another engine and it paints that engine's settings.

### Bugs found by building, not by reading

1. **An abort during module instantiation had nowhere to land.** `#booted` was armed just before
   `callMain`, so an Emscripten abort during runtime init — which arrives through `onAbort` — was
   emitted as an event while `open()` sailed on and waited forever for a first frame. The deferred
   is now armed *before* the module is built and raced against the boot work. Found by a test
   written for exactly that case, which hung.
2. **The memory stick path had `PSP` twice.** `#writeAssets` was passed `<userDir>/PSP` and then
   appended `/PSP/PPSSPP_STATE`, so a save state was written where PPSSPP would never look.
3. **The published package could not resolve its own emulator.** `src/loader.ts` resolves the glue
   relative to itself — `dist/native/ppsspp.js` once compiled — while `make wasm-build` copied the
   artifacts to `src/native/`. Nothing would ever have looked there. Found while writing
   `release.yml`, which is what made the question "can this actually be released" concrete.
4. **`files: ["dist/", "src/"]`** would have shipped tens of megabytes of build output twice.
5. **The demo could not resolve a bare specifier.** `dist/` imports `@wasm-gaming/engine-specs` by
   name and a browser cannot resolve that. Found by opening the page, not by reading it — the
   panel silently rendered nothing. Fixed with an import map and a copy in `site/vendor/`, no
   bundler involved.
6. **`INCOMING_MODULE_JS_API` takes only names Emscripten knows.** Listing `ppssppEvent` and
   `pthreadPoolSize` there earned `invalid entry` warnings. It does not matter — `MODULARIZE`
   emits `var Module = moduleArg`, so a host's own properties arrive on the module regardless —
   but the declaration was wrong and is now the runtime's own names only.

### A decision that was wrong, and how it was corrected

Round 3 of the build hit x86 intrinsics in `ext/at3_standalone`. The response was to enable
Emscripten's SSE-to-wasm translation with `-msse -msse2`, on the reasoning that it is a supported
feature and keeps the vectorised audio decode. It compiled, and it was the wrong call.

One target later `Common/CommonFuncs.h` included `<x86intrin.h>` — the kitchen-sink header — which
pulls in `ammintrin.h` (SSE4a) and `fma4intrin.h` (FMA4). No wasm toolchain implements those and
none will. There is no flag that gets past it; `-msse3` and friends would only have moved the wall.

The cause was upstream's own `ppsspp_config.h`, which maps `__EMSCRIPTEN__` to `PPSSPP_ARCH_X86`
with `PPSSPP_ARCH_SSE2` — reasonable when the target was asm.js, false now. Patch 0002 gives wasm32
its own `PPSSPP_ARCH_WASM`, modelled on the `RISCV64`, `MIPS` and `LOONGARCH64` branches already
sitting beside it, so it is the idiomatic shape for that codebase rather than an exception carved
for us. `-msse`/`-msse2` were dropped in the same patch: nothing reaches for x86 intrinsics any
more, and leaving them would advertise a capability the build does not use.

**The lesson, written down so it is not re-derived:** the SSE approach treated a symptom that
upstream's architecture claim was producing. Deferring the structural fix cost a round.

### A bug in upstream, not in the port

`Common/Math/CrossSIMD.h:1682` calls `LoadR24x3_One`, which exists nowhere in the tree. The real
name is `LoadF24x3_One`. It sits in the scalar fallback, which only compiles on a target with
neither SSE nor NEON — so this build is the first to reach it, and the typo has never been caught.

**Correcting the name alone would compile and be wrong.** The SSE, NEON and LOONGARCH
implementations of `LoadF24x4` all shift four lanes left by 8; `LoadF24x3_One` loads three and
zeroes W. Patch 0003 writes out the four-lane semantics the other three share.

This one is independent of WebAssembly and should be sent to `hrydgard/ppsspp` on its own.

# Extension · 2026-08-23 · closing rule for session files, and a rename that was reverted

**Summary.** `SESSIONS/` gains a completion rule, and a proposed rename of the folder to
`ROADMAP/` was carried out and then reverted within the same session.

## The closing rule

A file is now understood as one **body of work**, not one sitting — several sessions may extend
it, and one session may open more than one. When everything it set out to do is done:

1. Append a final `## Walkthrough · as completed` — what landed across the whole body of work,
   not a summary of what was planned.
2. Rename it from `.session.md` to `.session.completed.md`.

Read at a glance, the folder then answers the two questions that matter: `*.session.md` is open,
`*.session.completed.md` is finished. Nothing is deleted and nothing leaves the folder.

A file closes only when its `Next` is empty. Work being **abandoned** rather than finished is
said so in the walkthrough: an abandoned item closed quietly is indistinguishable from a
forgotten one.

This also fixes a real gap noted earlier in this session — that "what remains" was scattered
across four documents with no single place to look. `Next` is now a required section rather than
one this file happened to have, and the open/closed split makes the folder itself the index.

## The rename, and why it was reverted

`SESSIONS/` was renamed to `ROADMAP/` and the files stripped of their `.session` infix, on the
reasoning that the completion rule turns these files into forward-looking plans rather than
backward-looking records, and that a folder called `SESSIONS` undersells that.

Reverted immediately afterwards, on the author's call. `SESSIONS/` it is, and the `.session.md`
naming stays — which also keeps it consistent with `engine-specs`, where the convention came
from, and where a reader of one repository can navigate the other without relearning anything.

Recorded rather than quietly undone, because it is exactly the kind of turn this rule exists to
preserve: the completion rule survived the rename being dropped, and the two were separate
decisions that could easily be misremembered as one.

## Not done

Nothing in this extension changes code. `Next` above is untouched and still stands.

### Correction · 2026-08-23 · the `.session` infix is dropped

Files in `SESSIONS/` are named `YYYY-MM-DD_HHhMM.<summary>.md`, and close as
`.completed.md`. The `.session.md` naming described in the extension above is superseded: the

**Summary.** `Next` items 1 and 2 are done and item 5 with them: a build round now

## Where this repo actually was

## Walkthrough · as built

### 1 — a round is a whole round, and it pays for the next one

`make wasm` passes ninja `-k 0`; `WASM_KEEP_GOING=` restores the old behaviour for
bisecting a single target. The CI job caches ccache (through Emscripten's own
`EM_COMPILER_WRAPPER`, so ccache sees a clang command line rather than emcc's Python
driver) and `/emsdk/upstream/emscripten/cache`, keeps the whole round as a `build.log`
artifact, and writes the `FAILED:` lines into the run summary.

The first round with all of it found three failures at once instead of one. That is the
whole argument for the change, and it was settled in a single run.

### 2 — the last three compile errors, all of them upstream's

- **0004** completes the no-SIMD branch of `Common/Math/CrossSIMD.h`:
  `Vec4F32::WithLane3From` and `AnyCompareBitsSet(Vec4S32)`, both implemented by the
  SSE, NEON and LSX branches, both used by `GPU/Common/`, neither present in the scalar
  one.
- **0005** gives `FakeJit` the `GetCodeBase()` that `JitInterface` declares pure
  virtual. Without it the class is abstract and `CreateNativeJit()` cannot instantiate
  what it falls back to on every architecture without a native JIT — which, after 0002,
  is this one.
- **0006** builds the post office's POSIX socket backend under Emscripten.
  `postoffice.c` compiles unconditionally and calls into whichever `sock_impl_*.c` the
  platform list selects; Emscripten sets `UNIX` but not `LINUX`, so it selected none.

### 3 — the patch series can now reach inside a submodule

0006 needed a fix in `ext/aemu_postoffice`, and the previous session had recorded that
the series could not reach there: `git apply --3way` in the PPSSPP worktree has no blobs
for a submodule's files, so the three-way merge has nothing to merge against. Patches
under `native/patches/submodules/<submodule path>/` are now applied in the submodule's
own worktree, and `git submodule update` gained `--force` so a second `native-checkout`
resets what they dirtied.

The first of them fixes aemu_postoffice's `SO_NOSIGPIPE` guard, which reads
`#ifndef __linux__` — "not Linux, therefore BSD" — and is wrong for every other
POSIX-ish target.

### 4 — it links

`ppsspp.js` (387 KB), `ppsspp.wasm` (16 MB), `ppsspp.data` (22.6 MB). The glue exports
exactly the six members `src/module.ts` declares and nothing more, it is an ES6 module
with a default export, and the `-sPTHREAD_POOL_SIZE=Module['pthreadPoolSize']||…`
expression is emitted verbatim, so `config.threads` genuinely sizes the pool.

CI round 8 did all of this from a clean checkout — patch series, submodule patches,
compile, link, artifact upload — and came back green.

### 5 — cross-origin isolation, both halves

`src/loader.ts` checks `crossOriginIsolated` before importing the glue and throws an
error naming both headers. `=== false`, not a falsy test: outside a browser the global
does not exist, and a Node host driving this package through its own loader has no
`SharedArrayBuffer` problem to be warned about. The demo carries `coi-serviceworker`
(MIT), copied into `site/demo/` by `make site` — beside the page rather than in
`site/vendor/`, because a service worker's default scope is its own directory.

## Bugs found by building, not by reading

- **A failing build reported success.** A `run:` step's default shell is `bash -e {0}`,
  without `pipefail`; `shell: bash` is what adds it. `make wasm-release | tee build.log`
  returned tee's status, so round 7 was green with three compile errors in it, and only
  went red incidentally because the artifact upload found nothing.
- **Neither cache was saved.** `actions/cache` saves in a post step guarded by
  `success()`. While a port is in progress every round is a failed round, so the cache
  existed exactly when it was not needed. Restore and save are separate steps now, the
  saves are `if: always()`, and the build step carries `continue-on-error` so it cannot
  end the job before they run. The job's verdict is applied by a final step.
- **`emscripten_sleep()` in a pthreads build aborts the calling thread.** Upstream's
  `sleep_ms`/`sleep_us`/`sleep_precise` take an `__EMSCRIPTEN__` branch that calls it,
  which is an ASYNCIFY primitive: without `-sASYNCIFY` it does not sleep, it aborts.
  A browser build hits this within a second of starting. **0007** guards that branch on
  `__EMSCRIPTEN_PTHREADS__` so a threaded build takes the POSIX path — a worker can
  block for real. Same shape as 0002: a leftover from when the target was asm.js.
- **SDL3 takes the canvas by CSS selector, not by `Module.canvas`.** Its Emscripten
  video driver reads `SDL_HINT_EMSCRIPTEN_CANVAS_SELECTOR`, defaulting to `#canvas`,
  and fails window creation outright if nothing matches — which is what
  `SDLGLGraphicsContext::InitSurface: no window or GL context` turned out to mean. SDL2
  took the element from the module; SDL3 does not. **This contradicts what
  `src/module.ts` documents today**, and it is a contract question rather than a demo
  detail: the SDK builds a *new canvas per restart*, so it cannot call them all
  `canvas`. Not fixed yet — see `Next`.

# Extension · 2026-08-23 · a round that ends in a browser, and four walls behind the first

**Summary.** Blocking item 1 of the pending register is diagnosed, measured and
addressed, and three bugs nobody was looking for came out with it — one of them in the
*published* package. The port now instantiates, creates its window, registers its main
loop and returns from `callMain()`. It does not yet run.

The lasting change is not any of the patches. It is that a build round no longer ends at
"it linked": it ends with a verdict from a real browser.

## Where this repo actually was

The pending register said item 1's first step was not a fix but an instrument, and that
was right. The evidence for "the tab dies after `ThreadManager::Init`" was a person
watching a tab die. `-sASSERTIONS` was wired to nothing. The browser half of a round did
not exist, so every question about the browser cost a human afternoon.

`-sPROXY_TO_PTHREAD` stood recorded as "the candidate needing the least PPSSPP surgery".

## Walkthrough · as built

### The instrument, before any fix

`make smoke` boots the built artifacts in headless Chromium, driven over CDP, served
cross-origin isolated with the headers set directly rather than through a service
worker. No Playwright and no test framework: Node 22 has a `WebSocket` client and
Chromium speaks CDP, so the dependency list is empty.

**The signal is a heartbeat on the browser's main thread**, installed before
`callMain()` and read from outside afterwards. If `main()` holds that thread, the
interval cannot fire and the page cannot answer — so the runner reports `BLOCKED`
instead of hanging. A tab that stops answering is not missing evidence; it is the
measurement.

It was checked against three fakes — one that boots, one that blocks the main thread on
purpose, one whose factory never resolves — before being pointed at the emulator. An
instrument that cannot fail is not an instrument.

`make wasm DEBUG=1` adds `-sASSERTIONS=2`, `-sSTACK_OVERFLOW_CHECK=2`,
`-sPTHREADS_DEBUG=1` and `-g2`. All four are **link** flags, so instrumenting a round
costs a relink of a couple of minutes rather than a rebuild of 1118 targets. That is the
whole reason measuring is now cheaper than guessing.

In CI both are `workflow_dispatch` inputs, and the smoke run is a separate job: the
emsdk container has no browser, and moving a 40 MB artifact to a runner that already has
Chrome costs less than installing one per round.

### Then four walls, each of which was hiding the next

| Round | How far it got | What stopped it |
| --- | --- | --- |
| 10 | `instantiating` | waiting on run dependencies — cause not yet visible |
| 12 | `instantiating` | `404 /ppsspp.data` — named, once the runner could name it |
| 13 | inside `SDL_CreateWindow` | assertions tripwire on `Module['requestFullscreen']` |
| 14 | `callMain returned` | worker pool exhausted, then a blocked main thread |
| 15 | `callMain returned`, 5 frames | `ThreadFrame()`'s condition variable |

The order matters more than any single entry: **none of these was visible until the one
before it was fixed.** The original question — does `main()` block the browser's main
thread? — could not be answered until rounds 12 and 13 were out of the way, and the
answer when it came was yes, exactly where reading the source had predicted.

### 0008 — the GL loop belongs to the browser

`SDLGLGraphicsContext::NeedsSeparateEmuThread()` is `true`, so PPSSPP takes its OpenGL
path, where **the thread that owns the GL context is `main()`**. Its loop calls
`ThreadFrame()`, which waits on a condition variable until the emu thread submits a
frame. Correct wherever the render thread is a thread of our own; fatal where it is also
the thread the browser needs for input, for compositing, and for the WebGL swap that
only happens on returning to the event loop.

The loop body is lifted into `oneIteration()` — the two `break`s become `return false`,
nothing else moves — and Emscripten drives it from `emscripten_set_main_loop` at 0 fps,
which means `requestAnimationFrame`. Native builds run the same body in the same `while`
as before.

**This supersedes the pending register's preference for `-sPROXY_TO_PTHREAD`.** That
flag would move `main()` to a worker and take the render thread with it, turning the
problem into WebGL-from-a-worker, which needs OffscreenCanvas or proxied GL. Keeping the
GL context on the main thread — where a browser wants it — needs neither. The earlier
text stands as it was written; this is the reversal, said out loud.

Round 14 confirmed the patch does its job: `handleException: unwinding` followed by
`callMain returned`, where before it had blocked inside `callMain`.

### 0009 — and it must not block once it is there

Five animation frames later it stopped again, on the same condition variable, now
reached from inside the animation callback. Under Emscripten an empty queue now means
"no frame yet": return, let the event loop turn, be asked again next frame. A partly-run
frame resumes where it stopped, because nothing else touches GL in between.

## Bugs found by building, not by reading

1. **The published package could not find its own `.data`.** `src/loader.ts` passed
   `locateFile` only when a host supplied one. Emscripten resolves the two halves of its
   own output by different rules: with `-sEXPORT_ES6` the `.wasm` is found relative to
   the glue through `import.meta.url`, but the file-packager code from `--preload-file`
   asks for `ppsspp.data` by a bare relative name, which the browser resolves against
   **the document**. The glue ships inside `node_modules` and the page does not, so the
   `.data` would have 404'd on every real host — silently, since the run dependency is
   never cleared and `start()` simply never settles. The demo never saw it because it
   drives a stub. This one was shipping.
2. **The instrument broke what it was pointed at.** SDL3 ends `Emscripten_CreateWindow`
   with `Module['requestFullscreen'] = ...`; `-sASSERTIONS` installs a getter-only
   tripwire on every runtime symbol missing from `-sEXPORTED_RUNTIME_METHODS`, and the
   glue is an ES module, so the assignment is in strict mode and throws rather than
   failing quietly. Seeding the property is what stops the tripwire being installed. An
   observer effect, and worth its own line: the first instrumented round measured the
   instrument.
3. **The worker pool is sized for a deadlock, not for speed.** Emscripten grows its pool
   by returning to the event loop, and a blocked render thread never does — so a pool
   that runs out mid-boot stops rather than slows. `Tried to spawn a new thread, but the
   thread pool is exhausted` at 16; 8 was not enough. The comment on `poolSize()` in
   `src/ppsspp-wasm.ts` justifies its floor of four on throughput grounds, which is the
   wrong reason for the right shape of number. See `Next`.
4. **The instrument buried its own signal.** Emscripten's "still waiting on run
   dependencies" lists every preloaded file and repeats every few seconds — around a
   thousand lines in a two-minute run. The count is the information; the names are not.
   Found by using it once for real, which is the only way this kind of thing is found.
5. **The Actions cache is branch-scoped.** The 2m52s of the previous session holds only
   within a branch lineage: rounds 7–9 saved on `claude/continuamos-2aaqye`, so the
   first round on a new branch paid 10 minutes instead of 3. Seeding from the default
   branch would fix it for every branch at once.

## Walkthrough · as built

### The verdict is now a grade, not a pulse

| Verdict | What the canvas looked like | Exit |
| --- | --- | --- |
| `DRAWING` | More than one colour, in at least two samples. | 0 |
| `CLEARED, NOT DRAWN` | One flat colour, in every sample. | 1 |
| `BLANK` | No opaque pixel ever, across every sample. | 1 |
| `NO PICTURE READ` | The sampler itself failed. | **2** |

`CLEARED, NOT DRAWN` is the row the whole design turns on. **Every renderer clears its
target**, so a port that comes up and draws nothing does not leave an *empty* canvas — it
leaves a perfectly uniform one. A check that asked "is there anything on the canvas?"
would call that a pass, and would have called round 16 a pass no matter what it drew.
Counting distinct colours is what separates a picture from a clear.

`NO PICTURE READ` exits **2** rather than 1 on purpose. The other three are findings
about the port; that one is a finding about the runner, and a broken instrument reported
as a failing build is how a red round gets blamed on the wrong half.

### Two mechanics, both of which had to be chosen rather than assumed

**`preserveDrawingBuffer`, forced from outside.** A WebGL drawing buffer is cleared the
instant it is composited, so by the time anything outside the frame looks at it there is
nothing left to see. Emscripten never asks for the attribute that keeps it, so the
harness wraps `HTMLCanvasElement.prototype.getContext` before the module loads and merges
it in.

That is an observer effect and is labelled as one in the source, because this port has
already been bitten once by an instrument changing what it measured — the `-sASSERTIONS`
tripwire that killed `SDL_CreateWindow` in round 13. What it changes: the implicit clear
between frames goes away. PPSSPP clears its own target every frame, so it *should* not
change what is drawn. A `DRAWING` verdict that only appeared with this flag on would be
the thing to distrust.

**`drawImage`, not `gl.readPixels`.** `readPixels` reads whichever framebuffer is
currently bound, so using it would mean binding, reading and rebinding — and **patch
0009 is precisely the change that lets a frame sit half-finished between animation
frames**. Reaching into GL state at that moment is the instrument corrupting the run.
`drawImage` asks the browser for the canvas's own contents and leaves the bindings alone.
The sample goes into a 120×68 scratch canvas: a quarter of the drawing buffer, small
enough to summarise four times a second, large enough that a menu does not average down
to one colour.

### The fakes are kept this time

`make smoke-selftest` points the runner at five modules in `tests/fakes/`, each shaped
like the Emscripten glue and each built to land on exactly one verdict: `draws`,
`clears`, `blank`, `blocks`, `hangs`. All five as specified, run locally against a real
Chromium.

The previous session checked its verdicts against fakes like these and then did not
commit them, so the next change to the runner — this one — started with nothing to check
itself against. `clears` is the one that earns its keep: it is what turns "a uniform

In CI the selftest runs **before** the emulator boots, in the same job. A verdict about
the port is only worth having once the thing issuing verdicts has been checked.

### What it costs

A build that never draws now runs to the full timeout instead of settling after eight
seconds, because the early exit requires the answer to be *yes*. That is the right price:
"nothing was drawn" is the slowest thing here to be sure of, and calling it early is how
an instrument starts lying. `--settle` is a flag now so the selftest can use two seconds
where a real round uses eight.

### Correction · 2026-08-24 · round 19, and the silence was never evidence

**This withdraws the central inference of the round 18 entry.** That entry read two
minutes of PPSSPP saying nothing as a stalled emu thread. It was the log level.

`Config::Load()` calls `LogManager::LoadConfig()`, which reads a level per channel from
the ini and falls back to `LogLevel::LERROR` when the entry is missing. A smoke run boots
on a fresh memory stick, so there is no `[Log]` section and **every channel lands on
LERROR**. `LINFO` is 4, `LERROR` is 2, and `LogLine` drops anything numerically above the
channel's level. From the moment the config loads, the entire boot is invisible —
and everything the round 18 transcript *did* contain was logged before that point, which
is exactly why it appeared to stop where it did.

No patch was needed to fix it. `NativeInit` applies the command line *after* the config,
so `--loglevel=4` wins, and the harness now passes it to `callMain`.

**With PPSSPP talking, the port gets far further than three rounds of inference had it.**
Round 19's boot, in order: the memory stick created, `switchScreen('Logo')`, a real
WebGL2 context (`GPU Vendor : WebKit ... OpenGL ES 3.0 (WebGL 2.0)`), thin3d preset
shaders, audio open, `EmuTread_Start`, `GLRenderManager::ThreadStart`, `Entering separate
emu thread`, inflight frames set to 3, `NativeInitGraphics` **completed**, `EmuThread:
Entering loop`, and then the whole UI atlas — 152 images rasterised and packed into
1024x327. Every one of those is a line nobody had seen.

The last line of the run is:

```
40:39:705 SDL/SDLGLGraphicsContext.cpp:494 I[G3D]: SDL SwapInterval: 1
```

That log lives inside the swap-interval callback, which `GLRenderManager::Run()` calls
**only in its `PRESENT` branch**. So the emu thread built a complete frame, pushed
`SUBMIT` and `PRESENT`, and the render thread pulled and ran them. One full frame was
produced and presented. Then the emu thread stops producing, and the render loop spends
the next two minutes finding an empty queue.

**The emu thread did not die.** Round 18 was linked with `-sPTHREADS_DEBUG=1`, and its
full 760-line log contains no thread exit, no abort, no unwinding from any worker. It is
alive and not producing.

**And the sharpest thing in the numbers, which now reads differently.** `14 draw calls
(0 with the default framebuffer bound), 2 clears (0 to it), 2 framebuffer binds`. That is
the presented frame — and **not one of its draws or clears targeted the canvas**. A UI
frame that PPSSPP considered finished enough to present never rendered to framebuffer 0.
Whatever the emu thread is waiting for, the frame it did produce went somewhere invisible.

**What is in this round:** patch 0010 puts upstream's own push/pull trace behind a
define. `GLRenderManager` already carries a complete account of the handshake — which
frame was begun, which task pushed, which pulled and run, which wait is being sat in —
written by upstream and left behind `#if 0`, which no build can switch on. Adding
`defined(PPSSPP_GL_TRACE)` makes it `make wasm GLTRACE=1`, and a hunk in
`Common/CMakeLists.txt` scopes the define to the single file with the VLOGs so turning
it on costs one object rather than invalidating the ccache for 1118.

**`Next`, superseding the round 18 list:**

1. **Run the trace.** It sees both sides of the handshake, and one side has gone quiet.
2. **Find out why the presented frame never bound framebuffer 0.** It may be the same

3. **Rule out UPnP** — unchanged, and cheaper than either of the above.
4. **Settle the pool default**, **the canvas selector**, **the bridge**, **the real

**A smaller finding, recorded so nobody re-derives it.** `--loglevel=4` is also stat'd as

### Correction · 2026-08-24 · rounds 21 and 22 — the stall is found and fixed

**Round 21 pointed at the wrong half, and that was the useful part.** Patch 0011's
markers came back twenty lines long: **two complete passes of `NativeFrame`**, both
reaching `ProcessScreenSwitches`, and no third. So the update half was never the
problem — the thread was dying below the markers, in the tail of the frame.

**The bug is at the very end of `NativeFrame`**, in the menu's fallback throttle:

```cpp
float refreshRate = System_GetPropertyFloat(SYSPROP_DISPLAY_REFRESH_RATE);
static double lastTime = 0.0;
if (lastTime > 0.0) {
    int sleepTimeUs = (int)(1000000 * ((1.0 / refreshRate) - diffTime));
    if (sleepTimeUs > 0) sleep_us(sleepTimeUs, "fallback-throttle");
}
lastTime = time_now_d();
```

On SDL that rate is `g_RefreshRate`, copied verbatim from
`displayMode->refresh_rate`. SDL documents that as **0 when it cannot determine one**,
and 0 is what the Emscripten video driver reports — a browser cannot be asked what the
monitor is doing. `1.0 / 0` is `+inf`, and `(int)(1000000 * inf)` saturates to `INT_MAX`
under wasm's non-trapping float-to-int: **2147483647 µs, a 35-minute sleep inside a frame
that never returns.**

And `static double lastTime = 0.0` is why it presents as *exactly two frames*: the first
takes the `lastTime > 0.0` branch as false and only records the time; the second computes
the sleep and is gone. Every measurement from rounds 17 to 21 falls out of that line, and
none of them had to be guessed at.

Patch 0012 closes it in two places — `SDLMain` keeps its own 60 Hz default instead of
overwriting it with zero, and `NativeApp` defends the division so no platform reporting 0
(or NaN, which the `!(x > 0)` form also catches) can stop the emu thread dead. Neither
hunk is WebAssembly-specific. **It is an upstream bug that needed a platform with no
queryable refresh rate to show itself**, and it is the sixth of that family this port has
turned up.

**Round 22 says it worked, and by how much:**

| | round 21 | round 22 |
| --- | --- | --- |
| `NativeFrame` passes | 2 | **174** |
| `PUSH: BeginFrame` | 2 | **174** |
| `PULL: SwapFunction()` | 2 | **174** |
| GL draw calls | 14 | **159810** |

PPSSPP now runs continuously for the whole two minutes instead of stopping after 320 ms.

**And the verdict is still `BLANK`**, which is the instrument doing its job rather than a
disappointment:

```
GL: 159810 draw calls (0 with the default framebuffer bound),
7054 clears (0 to it), 7054 framebuffer binds.
```

**Not one of 159810 draws and 7054 clears ever had the default framebuffer bound.** This
is no longer a suspicion, it is the whole remaining bug. `GLQueueRunner::fbo_unbind()`
binds `GL_FRAMEBUFFER, g_defaultFBO` with `g_defaultFBO == 0`, and Emscripten translates
a zero name to `null` — exactly what the harness counts as the canvas. Zero out of 7054
binds were `null`, so **`fbo_unbind()` never ran**, so no render step ever had
`pass.render.framebuffer == nullptr`. PPSSPP is rendering every step into a framebuffer
of its own and never rendering to the backbuffer at all.

That is precisely what the `offscreen/` fake was built to represent, and it is now the
real thing rather than a hypothetical.

**`Next`:**

1. **Find out why no render step targets the backbuffer.** The counters say it never
   happens; the reason is in how the steps are built, not in the queue runner.
2. **Rule out UPnP** — unchanged.
3. **The pool default**, **the canvas selector**, **the bridge**, **the real loader** —
   unchanged.
